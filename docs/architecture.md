# Architecture

The toolkit is organized in layers: reusable workflow stages, consumer examples, declarative project configuration, and local validation/automation. Read-only CI workflows cover Python, npm Node, Bun, Docker, Terraform validation, Ansible, Security and Backup. Separate workflows handle image publication, SSH container deployment and tagged GitHub releases. Reusable workflow YAML must be stored in `.github/workflows/` for GitHub to discover it; this platform requirement takes precedence over a separate top-level `workflows/` folder.

Configuration is descriptive. The validator never runs configured commands. Consumer workflows should map only supported config values to fixed actions and trusted repository scripts; avoid evaluating values as shell source. The policy checker rejects mutable third-party action references, broad `write-all` permissions, direct interpolation of untrusted event/input contexts into shell, and checkout in `pull_request_target` jobs. Security check exceptions must include a check, reason, owner, and review date. Python CI pins its lint and test tool versions in the workflow; a requirements file is project-controlled and should contain reviewed pins. Node CI requires a checked-in npm lockfile and uses `npm ci`.

Scaffolding and CLI validation cover Python, Node.js, Dockerized application, and Terraform starter templates. Terraform CI installs an exact CLI version with checksum verification, formats and validates without backend credentials, and scans IaC misconfigurations. Ansible, Security and Backup workflows validate caller code and local fixtures only; they do not connect to client systems. Bun is supported by a separate reusable workflow, not a generated starter. Kubernetes validation and deployment remain future extensions. Remote deployment, GitHub Environment approval behavior, registry access, and release publication require GitHub settings and target infrastructure and have not been exercised from this local workspace.
